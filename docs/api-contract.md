# REST/UI contract

Base `/api/v1`. JSON success `{data:T,meta?:{page:number,page_size:number,total:number}}`; error `{error:{code:string,message:string,fields?:object},request_id:string}`. UUID string IDs; UTC ISO timestamps; JSON snake_case. GET lists return `data:[]` with meta; page default1/page_size20(max100), `q`, optional module filters. Unknown JSON fields rejected for typed control payloads.

Cookie `tf_session` HttpOnly SameSite=Lax; CSRF token from GET `/auth/csrf` -> `{data:{csrf_token}}`, send `X-CSRF-Token` on mutations. Browser fetch credentials include. Tenant context `X-Tenant-ID` UUID on every scoped endpoint; server verifies membership/current status every request. Frontend remembers the selected tenant ID per user and browser tab in sessionStorage (no auth tokens), validates active membership before restoring it, and clears it on logout. Standard errors: 401 unauthorized,403 forbidden/mfa_required,404 not_found,409 conflict,422 validation,429 rate_limited. Request cancellation uses 499 `cancelled` (the nonstandard client-disconnect status); an exceeded request deadline uses 504 `timeout`. Internal failures remain 500 `internal`.

## Setup and authentication

GET `/setup/status`: `{initialized:boolean,version:string,oidc_enabled:boolean}`.
Normal startup atomically provisions the configured default superadministrator and tenant on an empty platform. Username `admin`, initial password `Admin@123456` are the local defaults; existing accounts are never overwritten. `/setup` is a legacy low-level initialization endpoint used only by explicit uninitialized test fixtures; the browser has no workspace wizard.
POST `/auth/login`: `{username?:string,email?:string,password,totp?:string,recovery_code?:string}` -> current user; username takes precedence and accepts either username or email; `mfa_required` if second factor needed.
POST `/auth/logout`: clears/revokes session.
GET `/auth/me`: `{user:User,tenants:Tenant[],permissions:Grant[],modules:Module[],platform_admin:boolean}`. With a selected tenant header it includes that tenant's capabilities; without, permissions empty but memberships listed.
User `{id,username,email,display_name,mfa_enabled,must_change_password,created_at}`. Tenant `{id,name,slug,status,created_at,quotas?:object}`. Temporary passwords must be changed before management; `password_change_required` denies management access until a different valid password is stored through `/auth/password`.
GET `/auth/sessions`: Session[] `{id,created_at,last_seen_at,expires_at,current}`; DELETE `/auth/sessions/{id}`.
GET `/auth/security-events`: own redacted account events `{id,action,request_id,changes,created_at}` with SQL paging. Password/MFA/session security changes persist events atomically with their mutation.
POST `/auth/password`: `{current_password,new_password,totp?:string}` revokes other sessions.
POST `/auth/reset/request`: `{email}` generic success regardless existence; SMTP outbox, never token in API response/logs. POST `/auth/reset/confirm`: `{token,new_password}`.
POST `/auth/mfa/enroll`: `{password}` -> `{secret,otpauth_url}` shown only while enrollment; POST `/auth/mfa/confirm`: `{totp}` -> `{recovery_codes:string[]}` once. POST `/auth/mfa/disable`: `{password,totp?:string,recovery_code?:string}`.
GET `/auth/oidc/start` redirects; GET `/auth/oidc/callback` verifies state/nonce/PKCE and issuer/subject binding.

## Tenancy and authorization controls

GET `/tenants` lists own tenants; platform admin GET `/platform/tenants` lists all; POST `/platform/tenants` `{name,slug,owner_email,quotas?}`; PATCH `/platform/tenants/{id}` `{name?,status?,quotas?}` platform only.
GET `/members`: Member[] `{id,user_id,username,email,display_name,department_id,position,role_ids:string[],status}`; POST `/members` directly creates an account and membership with `{username,email,display_name,password,department_id?,position?,role_ids:string[]}`; existing global accounts are never overwritten. New accounts require an initial password change. PATCH `/members/{id}` `{department_id?,position?,role_ids?,status?}`; POST `/members/{id}/transfer` `{owner_id}` moves owned records before suspension.
Direct global account creation requires platform_admin as well as tenant-scoped members:create, members:assign and delegable role authority. Other tenant administrators use optional invitations to existing or email-verified accounts.
GET `/invitations`: invitation metadata; POST `/invitations` `{email,department_id?,role_ids}` -> metadata (token delivered via SMTP); POST `/invitations/accept` `{token}` signed-in verified email matching invite.
GET `/departments`: Department[] `{id,name,parent_id:null|string}`; POST `/departments` `{name,parent_id?}`; PATCH `/departments/{id}` `{name?,parent_id?}`; DELETE guards referenced/nonempty/cyclic trees.
GET `/roles`: Role[] `{id,name,description,builtin,grants:Grant[]}`; POST `/roles` `{name,description,grants}`; PATCH `/roles/{id}` same; DELETE protects builtins/referenced roles; POST `/roles/{id}/copy` `{name}`.
Grant `{resource,action,scope,department_ids?:string[],read_fields?:string[],write_fields?:string[],unmask_fields?:string[],conditions?:Condition[]}`. Scope enum `self|department|department_tree|selected_departments|tenant`. Default deny; `*` fields means all nonsensitive readable/mutable fields, never arbitrary attributes. Conditions `{field,op,value}`, operators allowlisted `eq|in` (AND within grant; OR across matching grants), descriptor allowlists fields. Explicit named sensitive read field may be masked unless unmask listed.
GET `/permissions`: `{modules:Module[],scopes:string[]}` registry. GET `/members/{id}/permissions`: effective grants, authorized managers only.

## Resource modules and tickets

Module `{key,label,label_en,description,description_en?,fields:Field[],actions:string[],operations?:Operation[]}`. Operation `{key,label,label_en}` declares a registered custom action; callbacks are never serialized. Field `{key,label,label_en,type,required?,sensitive?,readonly?,options?:string[]}` type `string|text|number|boolean|enum|date`.
Builtins registered `tickets`, `dictionaries`, `settings`, `notifications`. Control resources have permissions `members,departments,roles,invitations,audit,files,jobs` with resource-appropriate actions (read/create/update/delete/export/import/assign). Account resources never bypass tenant control authorization.
ResourceRecord `{id,tenant_id,owner_id,department_id,version,data:object,capabilities:Capabilities,created_at,updated_at}`. Capabilities `{actions:string[],write_fields:string[],transitions:string[]}` is computed from the original record and matching action, scope, conditions and field grants before filtering data. `write_fields` means PATCH/update fields only. Other actions use their own field grants. Missing capabilities deny client mutations; the server always revalidates.  Field filtering changes `data`; envelope immutable. GET `/resources/{module}` lists permitted records; GET `/resources/{module}/{id}` detail; POST `/resources/{module}` `{owner_id?,department_id?,data}`; PATCH `/{id}` `{version,owner_id?,department_id?,data}`; DELETE `/{id}` expected version via query `version=N`. Server enforces all existing/resulting scopes and fields. PATCH department omission preserves assignment, `null` clears it, and a UUID assigns it. Clearing or assignment still checks resulting scope. Existing response envelopes represent an unassigned department as an empty string; clients treat empty/null as unassigned.
Tickets fields `title` required,string; `description` text; `status` enum open/in_progress/resolved/closed; `priority` low/normal/high/urgent; `customer_email` sensitive,string; `internal_notes` sensitive,text; optional `customer_name` string and `resolution` text. Initial status open. POST `/resources/tickets/{id}/transition` `{version,status,resolution?}` enforces valid edges open->in_progress->resolved->closed, resolved->in_progress, closed->open; resolving requires a fresh nonblank summary. Generic PATCH assignment requires assign action in addition to update; the dedicated ticket assignment action does not require update. Valid transition targets come from `capabilities.transitions`.
POST `/resources/{module}/{id}/actions/{action}` `{version,data}` invokes a registered operation under its own action, row scope and write-field authority, with core-managed validation, optimistic version and audit.
POST `/resources/{module}/export` `{columns:string[]}` -> Job; GET `/jobs/{id}/download` streams authorized CSV with current scopes/fields. POST `/resources/{module}/import` multipart CSV field `file`, max1MiB/max1000 rows, schema + scope validation, transaction all-or-nothing -> `{inserted:number}`.

## Files, jobs, audit and operations

GET `/job-types` requires `jobs:create` and returns an envelope array of UI-declared extension definitions `{type,label,label_en,description?,description_en?,resource,action,input_fields:Field[],result_fields:Field[]}`, filtered by the current tenant actor's registered resource/action grants. No callbacks or payloads are exposed. Discovery does not replace submission/execution authorization, scoped record checks or quotas. A registered `InputFields` nil slice retains API-only behavior; an explicitly empty slice declares a UI task accepting `{}`. Declared inputs use the existing field types/validation and reject undeclared keys before any custom validator.

Registered extension Job responses optionally include `definition:{label,label_en,description?,description_en?,result_fields:Field[]}` for human-readable task/result display. Result values retain current authority-fingerprint suppression. Exports and unregistered historical job types retain their existing shape. POST `/jobs` still requires `jobs:create` plus the definition's resource/action and a bounded JSON object; live authorization remains authoritative.

GET `/files`: metadata list; POST `/files` multipart `file`,owner_id?,department_id?, bounded size, safe generated storage keys -> File `{id,name,size,content_type,owner_id,department_id,created_at}`; GET `/files/{id}/download`; DELETE `/files/{id}`.
GET `/jobs`: Job[] `{id,type,status,attempts,max_attempts,error,error_code?,error_stage?,result?:object,capabilities:Capabilities,created_at,updated_at}`; GET `/jobs/{id}`; POST `/jobs/{id}/retry`; POST `/jobs/{id}/cancel`. Job statuses pending/running/succeeded/failed/cancelled. Durable leases/retries, tenant and actor revalidation. No raw errors with secrets. Typed error code/stage is safe for display and diagnosis. Result metadata is bounded and restricted to registered nonsensitive typed fields.
POST `/jobs` `{type,payload}` accepts only explicitly registered types and validates registered resource/action authority. Callback record services resolve current tenant-owned records and scopes; payload owner/department values cannot authorize targets. Handlers run outside long transactions with at-least-once execution and stable job ID for idempotency. Generation authority is fingerprinted; scope/field changes prevent successful publication and stale result metadata is withheld. Retry/cancel/delete require jobs:update plus the authoritative row capability.
DELETE `/jobs/{id}` removes a terminal job under jobs:update scope, queues result-object cleanup and releases its storage quota transactionally. Pending/running jobs must first be cancelled.
GET `/audit`: Audit[] `{id,actor_id,action,resource,record_id,request_id,created_at,changes}`; no credentials/token/secret fields.
POST `/audit/export`: `{columns:string[]}` creates an authorized audit CSV export job; download uses `/jobs/{id}/download` and current audit scope.
GET `/dashboard`: `{counts:object,recent_activity:Audit[],workload:Workload}`; Workload optional `open_tickets`, `urgent_tickets`, `running_jobs`, `failed_jobs`, `members` integer counts. All SQL predicates apply current record authority; status/priority classifications also require corresponding field-read authority. Unauthorized categories are omitted, not fabricated as zero. Activity names require corresponding read permission. No synthetic charts.
GET `/healthz`,GET `/readyz`; GET `/metrics` loopback/admin-protected or explicitly configured. Config TF_DATABASE_URL, TF_LISTEN default127.0.0.1:8090, TF_PUBLIC_URL, TF_DATA_DIR, TF_MASTER_KEY, TF_COOKIE_SECURE, TF_SMTP_HOST/PORT/FROM, TF_OIDC_ISSUER/CLIENT_ID/CLIENT_SECRET, TF_STORAGE_BACKEND local|s3 and S3 config. CLI `serve`, `migrate`, `check-config`, `version`. Developer DB local port55439; web Vite5178 proxies API/health to8090. Docker listens0.0.0.0:8090 with same-origin bundled web; Compose binds127.0.0.1:8090. SMTP development mailbox uses Mailpit.

## Internal support workflow

Tickets add `customer_name:string`, `resolution:text` and `reply` action. These fields remain optional in stored/create data. Moving into resolved requires a fresh nonblank resolution submitted with the status through transition or generic PATCH; update must cover both fields. `Capabilities.reply_kinds?:('reply'|'note')[]` advertises allowed composer kinds; absent means none.

| Endpoint | Input/result | Authority |
| --- | --- | --- |
| POST `/resources/tickets/{id}/assignment` | `{version,owner_id,department_id?:string|null}` -> filtered Record | Read original; assign original/resulting row; no update required. Target active tenant member, omitted department follows target, explicit null clears. |
| GET `/resources/tickets/{id}/activity` | Standard page/page_size -> TicketEvent[] with meta, newest first | Read current parent; reply/note body fields determine inclusion and total. |
| POST `/resources/tickets/{id}/replies` | `{version,kind:'reply'|'note',body}` -> `{record:Record,event:TicketEvent}` | Read parent, reply action, corresponding write plus readable body; note explicit read+unmask. |
| POST `/resources/tickets/{id}/transition` | `{version,status,resolution?:string}` -> Record | Existing update/status authority; resolved also requires resolution write and nonblank fresh value. |

TicketEvent `{id,ticket_id,kind,actor_id:string|null,actor_name,created_at,body?,from_status?,to_status?,owner_id?,department_id?:string|null,fields?:string[]}`. Kinds created/updated/assigned/status_changed/reply/note. Reply bodies map to description read/write, notes to internal_notes read/write+explicit unmask. Hidden conversation events are excluded entirely, including the count. Status and resolution details and changed-field names require corresponding current readable fields. System events never expose arbitrary before/after customer data. Legacy tickets accumulate activity from upgrade; no past events are invented.

Reply bodies are nonblank plain text <=4000 Unicode characters and <=8192 UTF-8 bytes. Closed/stale writes fail; parent version, immutable event and redacted audit commit together. Reply records communication and does not deliver email. Typed inputs reject unknown keys. Every history access rechecks current parent visibility; reassignment/revocation prevents old history access.

GET `/resources/tickets?queue=mine|active|resolved|closed|all` adds a queue predicate before authorization-filtered count/paging. mine is current owner AND open/in_progress; active is open/in_progress; resolved/closed exact status; all/omitted adds no queue predicate. Status-classifying queues also require a readable status predicate to prevent hidden-field inference. Unknown queue or queue on another module is 422. Existing q/field filters combine with the queue. Export retains its independent contract.

Migration 011 adds forced-RLS ticket_events with tenant-aware parent/actor references and runtime SELECT/INSERT only. Common resource writes and member ownership transfers produce safe activity atomically. Protected Owner activation adds reply with an audit entry; custom role grants remain unchanged. Role templates are reviewable new drafts, explicitly disclose customer_email/internal_notes read+unmask and never automatically persist or overwrite roles. See the [complete flow and reuse guide](support-desk.md).
