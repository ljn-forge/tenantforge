# Internal customer-support reference application

## Approved purpose

The user approved a Go/Vue multi-tenant administration framework with a complete customer-support example, and explicitly selected an internal support desk: employees register issues on customers' behalf, supervisors assign work, and agents process it. This extends existing tickets rather than creating an unrelated application. Existing accounts, custom roles and tenant records must survive upgrades. No automatic production demo seeding or external publishing/messages.

## Product flow

1. An administrator creates a support department, agent/supervisor roles using visible, reviewable templates, and accounts.
2. An agent registers a title, problem description, customer name/email and priority. The ticket starts open and belongs to its creator unless explicitly assigned.
3. A supervisor sees department tickets and assigns an active member and department using a dedicated assignment action. Assignment does not imply general editing permission.
4. The agent opens My active tickets, starts work, records a customer conversation or a private internal note, and sees an immutable activity history.
5. Resolving requires a nonblank resolution summary. The supervisor/authorized employee closes it. Resolved tickets can return to in_progress and closed tickets to open; a subsequent resolution requires a new summary.
6. Different tenant data and out-of-scope tickets are inaccessible. Contact details and internal notes follow explicit sensitive-field grants.

Replies are employee-entered records of customer communication. This does not send email to customers or introduce a customer login portal. Do not claim either behavior. Plain text is escaped by the UI; no rich-text dependency. Existing file/notification modules remain independently available; this flow does not imply ticket-linked attachments or outbound notifications.

## Backend contract (canonical additive amendments below)

- tickets adds action `reply` and fields `customer_name:string` and `resolution:text` (both optional for stored/creation compatibility). Existing fields and statuses remain. Resolution is required when moving into resolved, through either transition or generic update.
- POST `/resources/tickets/{id}/transition` accepts `{version,status,resolution?:string}`; resolving includes resolution and requires write access to status AND resolution under tickets:update. Other transitions omit resolution. A general PATCH cannot bypass this rule. Capabilities.transitions advertises resolved only when both fields are writable. Historical resolution remains the latest summary on reopen and is replaced on each resolve.
- POST `/resources/tickets/{id}/assignment` accepts `{version,owner_id,department_id?:string|null}`. A valid active target membership is required. When omitted, department follows the target member. Explicit null clears it. Require old record read plus tickets:assign on original/resulting rows, and optimistic version. Empty data must not require tickets:update. Return a normal filtered Record; if read access to the resulting row is lost, the frontend closes details/removes the record.
- GET `/resources/tickets/{id}/activity?page=1&page_size=20` returns paged `TicketEvent[]`, newest first. It requires tickets:read on the current parent. The count uses the same event visibility predicate as the data. Event shape: `{id,ticket_id,kind,actor_id: string|null,actor_name:string,created_at,body?:string,from_status?:string,to_status?:string,owner_id?:string,department_id?:string|null,fields?:string[]}`. Kinds: created, updated, assigned, status_changed, reply, note. Only safe metadata: no before/after customer snapshots or arbitrary audit content. Status fields require readable status; field names are restricted to readable fields; assignment metadata matches already-visible Record ownership. Actor identity denotes a ticket participant; it is not a member-directory listing.
- POST `/resources/tickets/{id}/replies` accepts `{version,kind:'reply'|'note',body:string}` and returns `{record:Record,event:TicketEvent}`. Nonblank <=4000 Unicode characters and <=8KiB UTF-8 body; reject unknown keys/kinds. Require current parent read and tickets:reply with corresponding write field: description for replies, internal_notes for notes. Reply bodies require current read access to description; note bodies require explicit read+unmask internal_notes. Closed tickets reject replies. Increment parent version, insert event and redacted audit together. Stale version conflicts without a duplicate event. No rewriting initial description or legacy internal_notes data.
- Optional additive Capabilities.reply_kinds `['reply','note']` lists currently permitted composer kinds. This is recomputed for each record with operation, scope, field-read/write/unmask and closed state; missing means none. Actions and capabilities never substitute for mutation authorization.
- Resource query `queue=mine|active|resolved|closed|all` is tickets-only. mine means owner=current user AND status in open/in_progress. active means open/in_progress. resolved and closed exact status; all has no extra predicate. Omitted preserves existing listing. Unknown values or queue on other modules yield 422. Combine with existing q/field filters and authorized SQL predicate before paging/count. Export remains its existing explicit contract, not a claimed queue export.
- New 011 migration creates ticket_events with tenant-aware resource parent FK and tenant-aware actor membership FK, RLS forced, runtime privilege limited to SELECT/INSERT, supporting pagination index. Actor deletion may null actor_id without losing history. Event insertion for ticket create/update/assignment/status changes is hooked into common resource writes so API, import and job paths cannot silently skip history. No synthetic history for old records; legacy record details show history from upgrade onward.
- System events carry no message body. Replies/notes are omitted entirely when their corresponding current field authorization is absent; hidden events do not contribute to total. Readable resolution may be included as body on resolved status events, otherwise omitted. Moving/permission revocation re-evaluates all history against current parent visibility.

## Frontend

Reuse existing resource table/filter/form, request epochs and typed field input. Preserve the generic resource route and existing labels used in acceptance. Tickets gain a business-specific queue toolbar and handling section in the existing drawer, with problem information, owner/assignment control, plain-text thread/activity, paging/retry, reply/note composer, resolve summary dialog and workflow buttons. No raw UUIDs as the primary task explanation. Private notes are clearly labeled. Show successful persisted records only, preserve drafts on errors, handle 409 with refresh, prevent duplicate submissions, and clear drafts/history on close/tenant/user/permission/record changes; stale asynchronous results cannot repopulate another context.

Roles page adds new-agent/new-supervisor template entry points for new drafts only. Agent: tickets read/create/update/reply scope self; supervisor: tickets read/create/update/reply/assign scope department, members:read and departments:read scope department. Read fields include ordinary fields plus explicit customer_email/internal_notes, with explicit unmask of those two. Writable fields for create/update include normal ticket fields and customer_email/internal_notes, but templates omit destructive/import/export/admin grants. Reply fields description/internal_notes only. Explain sensitive access in draft preview; templates never save or modify an existing role automatically. Backend delegation rules remain authoritative.

## Reuse decision

Reuse existing state graph, SQL authorization, transactions, validation, descriptors, generated UI, ownership assignment guards, redacted audit and schema migration tooling. Compared the local graph with looplab/fsm (https://github.com/looplab/fsm, Go FSM) and Temporal (https://docs.temporal.io/, durable execution platform). Neither adds needed behavior to this small existing graph; Temporal introduces a service boundary and an FSM library cannot provide tenant/field/transaction security. No new runtime dependency is selected; no claims about their current security/adoption rankings. Existing Vue/Element Plus components remain.

## Acceptance

Meaningful red-green tests for resolution bypass, reply/note field guards, closed/stale writes, current-scope history/counts, unknown queue, assignment without update, cross-tenant actor/parent references and history/audit atomicity. Existing tests pass. Production browser case creates actual department/roles/accounts, registers/assigns a ticket, checks agent scope, replies/notes/resolution/close/reopen, verifies a restricted viewer cannot retrieve internal history, verifies another tenant cannot retrieve it, and checks Chinese/mobile/dark handling. Docs explain business use, role setup, API, migration/backup and how developers reuse platform versus example-specific code. Local live cutover only after tests, backup and unchanged existing-data fingerprints (except audited protected Owner activation); fresh fixture acceptance never resets business data.
